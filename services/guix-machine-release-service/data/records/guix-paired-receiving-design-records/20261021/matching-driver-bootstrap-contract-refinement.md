With literal binary-identity matching, an unchanged baseline constructor without
check-target cannot produce a successful step5. Replacing that constructor with

## Proposed matching rule and role binding

Keep direct matching as the normal route: each side's selected driver supplies
both its build boundary and check-target. For the additive-boundary bootstrap
ONLY, permit a separately pinned source-qualified CDE checker as a qualified
tool if all of these facts are received:

* The original baseline and candidate constructors remain independently selected
  from their actual source graphs and are actually invoked to construct their
  own products. No current-main or newer-constructor substitution occurs.
* The checker is the exact current-owner CDE13 reconciliation candidate, not
  its historical driver, an installed global latest or a caller-selected
  executable. Its source identity, native interpreter/imported Guix/JSON closure,
  channels and fixed command are retained as a separate TOOL role.
* The checker calls the SAME shared target-receiving predicate as the selected
  constructor. For the bootstrap pair, independently demonstrate the complete
  predicate and declaration-reading dependency slice is byte-identical for both
  side constructors and the checker, or refuse this bootstrap rule. Names,
  signatures, target labels and unit-test success alone do not prove equivalence.
  No generic semantic-equivalence classifier or compatibility assertion is added.
* Current targets, schemas, canonical/registered store checks, profile/main-unit/
  host/instance/execution-role checks and actor-only/worker distinctions remain
  unchanged. A changed predicate/schema or constructor-specific target meaning
  is outside this additive bootstrap and remains unavailable, not no-regression.
* Each check invocation uses the Guix/channel identity appropriate to THAT side
  and proves CDE13's full imported-channel match. One observed Guix closure is
  not assumed valid for the other side. Products/store roots are independently
  retained and registration is checked before/after each read.
* The candidate checker has been independently received through the existing
  fixed qualified-tool source/native path before invocation. It has no build,
  receive, rollback, activation, profile, retention or live-health authority.
  Both actual products and every other stage still need real independent
  receiving; the tool qualification is not machine acceptance.

This rule changes the meaning of matching from exact whole-driver binary identity
to exact target-predicate/declaration-reader identity ONLY for a separately
qualified additive public boundary. It must be stated expressly in the Guix
source contract. It does not pretend the earlier step5 already permitted it.

The closed receiver derives the checker from the independently received exact
CDE change/tool enrollment in its existing request/source qualification; it does
not accept a new arbitrary checker program/path/recipe or alleged tool receipt.
If that enrollment cannot bind an actual original operation, execution stays
incomplete with an exact named prerequisite. No new registry, runner or authority
carrier is needed. The existing request keeps constructor and checker roles
distinct in its actual operation results.
